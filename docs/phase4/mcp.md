# エージェント向け MCP サーバー（Phase 4）

Blongo のコアは、自分が動かしているエージェントに MCP サーバーを1つ渡します。エージェントはこれで、同じプロジェクトのスレッドを読んだり、メッセージを送ったり、子エージェントに仕事を任せたり（`delegate_task`）、定期実行を登録したりできます。t3code の `t3_thread_*` に相当する道具です。

コード: `crates/blongo-core/src/mcp.rs`（JSON-RPC と配線）、`crates/blongo-core/src/orchestrator/tools.rs`（各ツールの中身）。

## 配線

```
エージェント ──stdio── blongo mcp-bridge SOCKET TOKEN_FILE ──unix socket── コア（McpServer）
```

- コアは起動時に `<data_dir>/mcp/s` で Unix ソケットを待ち受けます（フォルダ 0700、ソケット 0600）。
- エージェントのセッションを始めるたびに、ランダムなトークン（32 バイト、16 進）を作って `<data_dir>/mcp/<ランダムな32桁>.token`（0600）に書き、そのスレッドの ID と結びつけます。ファイル名はトークンとは無関係な乱数です。ソケットを作ったあと、フォルダは `-wx------`（0300）にするので、セッションは自分のファイル名は開けても、フォルダを一覧して他のセッションのトークンを探すことはできません。トークンはセッションの `Grant` が持ち、セッションが終わる（解放・停止・再起動）と削除・失効します。
- エージェントには「MCP サーバー = `blongo mcp-bridge <socket> <token_file>`」を設定で渡します。ブリッジは最初の1行で `blongo-mcp <token>` を送り、あとは stdio とソケットのバイトをそのまま中継するだけです（コアも GPUI も起動しません）。
  - Codex: `thread/start` の `config.mcp_servers.blongo`
  - Claude Code: `--mcp-config={"mcpServers":{"blongo":{...}}}`
  - ACP（Antigravity と汎用 ACP）: `session/new` の `mcpServers`
- ブリッジの実行ファイルは既定で「今動いている blongo 自身」（`current_exe`）です。`blongo serve` のときは `blongo-serve mcp-bridge` になります。
- `BLONGO_MCP=0` で無効にできます。

JSON-RPC は手書きの最小実装です（`initialize`、`ping`、`tools/list`、`tools/call`、通知は無視）。1行は最大 1 MiB。ツール呼び出しはそれぞれ別タスクで処理するので、待つツールが他の呼び出しを止めることはありません。

## ツール

| ツール | 内容 |
|---|---|
| `t3_thread_list` | 呼び出し元と同じプロジェクトのスレッド一覧（新しい順、状態で絞り込み可） |
| `t3_thread_read` | スレッドの最新メッセージ（ユーザーとアシスタント、各 16,000 字まで） |
| `t3_thread_create` | 同じプロジェクトに、呼び出し元の**子**としてスレッドを作る（最初のメッセージも送れる）。深さと同時数の上限は `delegate_task` と同じ |
| `t3_thread_send` | メッセージを送る（`queue` = 待ち行列 / `steer` = 実行中のターンに追加） |
| `t3_thread_wait` | 実行中のターンが終わるまで待つ（既定 10 分、最大 30 分。待ち切れても作業は止めない） |
| `t3_thread_interrupt` | 実行中のターンを中断する |
| `delegate_task` | このスレッドの子スレッドを作って仕事を任せる。`mode=wait`（終わるまで待って最終メッセージを返す）/ `async`（子の ID をすぐ返す） |
| `task_status` | 任せた仕事の状態と、終わっていれば最終メッセージ |
| `list_scheduled_tasks` | このプロジェクトの定期実行の一覧 |
| `schedule_task` | 定期実行を**提案**する（5 項目の cron、ローカル時刻。このスレッドへ送るか、毎回新しいスレッドを作るか）。提案は無効のまま作られ、ユーザーが設定画面で「Approve」を押すまで走らない |

## 安全のための決まり

- **プロジェクトの外は見えない**: どのツールも、呼び出し元スレッドのプロジェクトに属するスレッドしか扱いません。他のプロジェクトのスレッド ID を渡されても「unknown thread」と答え、存在するかどうかも漏らしません（`core_phase4.rs` の MCP テストで確認）。
- **トークンはセッションごと**: トークンファイルは 0600、ソケットは 0600 で、一覧できないフォルダの中。トークンなしや誤ったトークンの接続はすぐ切ります。セッションが終わればトークンは失効し、ファイルも消えます（スレッドをアーカイブしたあと古いトークンで接続しても断られることを `agents_cannot_escape_the_spawn_limits` で確認）。ただし、これは**ゆるい境界**です。トークンファイルのパスはブリッジの引数なので、同じユーザーのプロセスなら `/proc/*/cmdline`（macOS では `ps`）で読めますし、フォルダの権限も戻せます。つまり同じユーザーで動くプロセス（他のセッションのエージェントを含む）は、意図的に探せば他のセッションのトークンを使えます。トークンが守るのは、別のユーザーや、ファイルを当て推量で開くだけの相手です。エージェント同士を本当に分けるには、別ユーザーやサンドボックスで動かす必要があります（未対応）。
- **スレッドを増やす上限**（`delegate_task` と `t3_thread_create` の両方。どちらで作ったスレッドも呼び出し元の子になる）:
  - 深さは 2 段まで（子の子まで）。孫からはもう作れない
  - 1 つのスレッドが同時に抱える子は 4 つまで。数えるのは、実行中・ジョブ中・メッセージ待ちの子と、**まだ作成待ちの列にいる子**。グローバルなジョブ（ブランチ切替など）が列を止めている間に呼び出しを重ねても、上限をすり抜けられない（`core_phase4.rs` の `agents_cannot_escape_the_spawn_limits`）
  - 1 つのプロジェクトで、エージェントが作ったスレッドが同時に動くのは 8 つまで
  - 1 つのスレッドが作れる子は、動いていなくても（アーカイブしていないもの）合わせて 16 まで。動いていない子をためておく手は使えない
- **`t3_thread_send` で起こすのも同じ上限**: 動いていないスレッドにメッセージを送ると、エージェントがもう 1 つ動き出すのと同じなので、作るときと同じ上限で確かめます
  - エージェントが作ったスレッド（終わった `delegate_task` の子を含む）は、**その親**の同時 4 つと、プロジェクトの 8 つに数える
  - ユーザーが作ったスレッドを起こすときは、**送り手**の同時 4 つとプロジェクトの 8 つに数え、そのターンが終わるまで数え続ける
  - もう動いているスレッドへのメッセージは、その作業のあとに並ぶだけなので数えない
  - `core_phase4.rs` の `agents_cannot_wake_more_threads_than_they_could_start` で確かめた: 動いていない子を 10 個作って順に起こすと 4 つだけ動く。別の親が 4 つ起こしてプロジェクトが 8 つになると、ユーザーのスレッドも起こせない。終わった `delegate_task` の子 6 つを起こしても 4 つだけ
  - 子は親のフォルダ（ワークツリーを含む）で動き、親の会話は受け継ぎません（渡したプロンプトだけ）
- **定期実行は提案だけ**: `schedule_task` で作った定期実行は無効（`proposed_by` つき）で作られ、ユーザーが設定画面の Scheduled runs で「Approve」（オンにする）を押して初めて走ります。実行間隔は 15 分以上のものしか提案できず（`* * * * *` などは拒否。次の 500 回の間隔で確かめる）、承認待ちの提案は 1 プロジェクト 10 件まで。定期実行のターンも、承認ポリシーは全体の設定（ask / auto-approve）のままで、作ったエージェントより緩くはなりません
- **接続ごとの上限**: 1 つの接続で同時に走るツール呼び出しは 8 つまで（超えた分はすぐエラー）。返事の送り待ちは 32 件の有限の列で、読まないエージェントは自分の呼び出しが止まるだけです。同時に受け付けるブリッジは全体で 64 本まで
- **待ちの上限**: 待つツールは最大 30 分で返ります。待ちの途中でセッションが終わればエラーで返ります。
- **承認はそのまま**: 子スレッドや送られたメッセージで起きた承認要求は、普通どおりユーザーに出ます（自動承認の設定は全体の設定に従う）。MCP から承認を代行するツールはありません。
- **操作は通常のコマンドと同じ道を通る**: ツールが起こす変更は、UI からの操作と同じコマンド（`ThreadCreate`、`MessageDispatch` など）としてコアの判定を通り、イベントとして記録されます。

## 既知の制限

- **Windows**: Unix ソケットを使うので、Windows では MCP サーバーを起動しません（ログに理由を出して無効）。名前付きパイプ版は未実装です。
- **長いデータフォルダのパス**: ソケットのパスが Unix ソケットの上限（約 108 バイト）を超えると、MCP サーバーは無効になります（ログに理由を出す）。既定の場所（`~/.local/share/blongo`）なら問題ありません。短い別の場所（`$XDG_RUNTIME_DIR`）に逃がす処理は未実装です。
- **リモート環境**: `blongo serve` の中で動くエージェントには、サーバー側の MCP サーバーが渡ります（ツールの範囲はそのサーバーのプロジェクト）。
- MCP の resources / prompts / sampling は実装していません（tools だけ）。
